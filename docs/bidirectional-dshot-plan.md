# План: bidirectional DShot300 у проєкті `dshot-reader-embassy`

Мета: навчити RP2040 поводитися як ESC у двонапрямному режимі DShot300. Тобто приймати команди від контролера польоту (FC) і через ~30 мкс відповідати тим самим проводом значенням eRPM (обертів мотора).

Робота розбита на маленькі етапи. Кожен етап закінчується перевіркою, і до наступного варто переходити лише тоді, коли попередній точно працює. Так, якщо щось зламається, буде зрозуміло, де саме.

---

## Крок 0. Підготовка

Що знадобиться:

- плата RP2040 (як і зараз);
- контролер польоту з Betaflight **або** ваш `dshot-writer-test`, якщо ви доробите в ньому двонапрямний режим;
- логічний аналізатор або осцилограф (навіть дешевий аналізатор на 24 МГц підійде, але краще мати 50–100 МГц);
- спільна земля між FC і RP2040, рівень сигналу 3,3 В.

Підключення залишається як було: сигнал на **GPIO0**.

> Порада: тримайте аналізатор підключеним до лінії весь час. Більшість помилок у цій задачі — це помилки таймінгу, і їх видно лише на осцилограмі.

## Крок 1. Налаштувати FC на двонапрямний DShot300

У CLI Betaflight:

```
set motor_pwm_protocol = DSHOT300
set dshot_bidir = ON
save
```

Частоту циклу варто зменшити до 4 кГц, бо один обмін DShot300 займає ≈140 мкс і не вміщується в цикл 8 кГц (125 мкс):

```
set pid_process_denom = 2
save
```

**Перевірка:** на аналізаторі лінія в спокої має бути **високою**, а кадри складатися з коротких «провалів» донизу. Якщо лінія в спокої низька — двонапрямний режим не ввімкнувся.

## Крок 2. Зняти «еталонну» осцилограму

До того як писати код, запишіть кілька кадрів від FC і переконайтеся в параметрах:

| Що міряємо | Очікуване значення |
|---|---|
| Тривалість біта | 3,33 мкс |
| Низька частина біта «1» | ≈2,5 мкс (75%) |
| Низька частина біта «0» | ≈1,25 мкс (37,5%) |
| Тривалість кадру | ≈53,3 мкс |

Збережіть цей запис — далі з ним зручно порівнювати.

**Приклад.** Якщо FC шле газ 1000 з T = 0, кадр має бути `0x7D05`:

```
0111 1101 000 | 0 | 0101
газ = 1000      T   CRC (інвертована)
```

## Крок 3. Змінити тактування PIO на 12 МГц

Зараз дільник `10`, тобто такт 80 нс. Для відповіді (біт 2,667 мкс) це дає 33,3 такту — нецілу кількість, через що біти «пливуть».

З частотою 12 МГц (такт 83,3 нс) все ділиться рівно:

| Величина | Час | Тактів при 12 МГц |
|---|---|---|
| Біт команди DShot300 | 3,333 мкс | 40 |
| Біт відповіді (375 кбіт/с) | 2,667 мкс | 32 |
| Пауза перед відповіддю | ≈30 мкс | ≈360 |

```rust
// 125 МГц / 12 МГц = 10,4167
cfg.clock_divider = fixed::FixedU32::<U8>::from_num(125.0 / 12.0);
```

Дільник дробовий, тому з'являється джитер до одного системного такту (8 нс). Для DShot це неважливо.

> Якщо ви змінювали системну частоту RP2040 (за замовчуванням в embassy 125 МГц), перерахуйте дільник.

## Крок 4. Етап A — лише прийом інвертованих кадрів

Поки що **без відповіді**. Мета — стабільно читати кадри і бачити їх через USB.

Що змінюється порівняно з поточною програмою:

1. Пауза між кадрами тепер — це **високий** рівень, а не низький.
2. Початок біта — **спадаючий** фронт.
3. Читаємо рівень приблизно в середині біта (через ~20 тактів після фронту): низький рівень означає «1», високий — «0».

Фрагмент PIO-програми для цього етапу:

```
idle:
  set y, 31
idle_loop:
  jmp pin still_high   ; лінія висока — рахуємо далі
  jmp idle             ; впала — починаємо відлік спочатку
still_high:
  jmp y-- idle_loop    ; 32 × 2 такти ≈ 5,3 мкс тиші
  set x, 15
bit:
  wait 0 pin 0 [19]    ; спадаючий фронт + чекаємо до середини біта
  in pins, 1           ; читаємо рівень
  wait 1 pin 0         ; чекаємо, поки лінія знову підніметься
  jmp x-- bit
```

PIO записує біти «як на лінії», тобто інвертованими. CPU перевертає їх назад:

```rust
let raw = sm.rx().wait_pull().await;   // наприклад, 0x82FA
let frame = (!raw & 0xFFFF) as u16;    // 0x7D05
```

І перевіряємо CRC — у двонапрямному режимі вона **інвертована**:

```rust
fn frame_ok(frame: u16) -> bool {
    let v = frame >> 4;
    let crc = !(v ^ (v >> 4) ^ (v >> 8)) & 0x0F;
    crc == frame & 0x0F
}
```

**Перевірка:** у терміналі (`tio --output-mode=hex4 ...`) з'являються правильні кадри, а `frame_ok` майже завжди повертає `true`. Порахуйте частку кадрів з поганою CRC — вона має бути близькою до нуля.

## Крок 5. Винести кодування в окремий модуль і покрити тестами

Функції кодування (CRC, GCR, NRZI) не залежать від заліза. Їх зручно винести в окремий `no_std`-крейт, наприклад `dshot-codec`, і тестувати на комп'ютері звичайним `cargo test`, без прошивання плати.

Головна функція — `encode_reply()`. Вона з 12-бітного значення eRPM робить 21 біт рівнів лінії:

```
e12 (12 біт)  →  + CRC (4 біти)  →  4 нібли  →  GCR (4 × 5 біт)  →  NRZI + старт-біт  →  21 біт
```

Таблиця GCR:

```rust
const GCR: [u8; 16] = [
    0x19, 0x1B, 0x12, 0x13, 0x1D, 0x15, 0x16, 0x17,
    0x1A, 0x09, 0x0A, 0x0B, 0x1E, 0x0D, 0x0E, 0x0F,
];
```

Приклад тесту на значеннях з нашої осцилограми:

```rust
#[test]
fn reply_matches_waveform() {
    // 0x5F4 → слово 0x5F41 → GCR 10101 01111 11101 11011
    // → рівні лінії 0 1100110101010010 1101 (21 біт), вирівняні вліво
    assert_eq!(encode_reply(0x5F4), 0x66A9_6800);
}

#[test]
fn frame_crc() {
    assert!(frame_ok(0x7D05));
    assert!(!frame_ok(0x7D04));
}
```

**Перевірка:** усі тести проходять на комп'ютері.

## Крок 6. Етап B — відповідь фіксованим значенням

Тепер додаємо передачу, але відповідаємо завжди одним і тим самим числом. Так простіше перевірити таймінг.

### 6.1. Прив'язати одну ніжку до всіх груп PIO

```rust
let mut pin = pio.make_pio_pin(dshot_pin);
pin.set_pull(Pull::Up);      // у спокої лінія висока

cfg.set_in_pins(&[&pin]);    // для wait і in
cfg.set_jmp_pin(&pin);       // для jmp pin
cfg.set_out_pins(&[&pin]);   // для out pins (передача бітів)
cfg.set_set_pins(&[&pin]);   // для set pins і set pindirs (перемикання напрямку)

cfg.shift_out = ShiftConfig {
    auto_fill: false,                // без autopull: дані бере лише `pull noblock`
    direction: ShiftDirection::Left, // out pins, 1 бере старший біт
    threshold: 32,
};

sm.set_config(&cfg);
sm.set_pin_dirs(Direction::In, &[&pin]); // стартуємо як вхід
```

Зсув OSR вліво потрібен, бо `encode_reply()` кладе 21 біт відповіді у старші біти слова (`<< 11`). Autopull має бути вимкнений: інакше `out` сам тягнутиме дані з TX FIFO, і логіка `pull noblock` з запасним значенням у X перестане працювати.

### 6.2. Перемикання ніжки з читання на запис і назад

Це ключова частина. Робимо її в PIO, а не з CPU: між кадром і відповіддю лише ~30 мкс, а async-задача в embassy може прокинутися із затримкою.

```
  set y, 22
delay:
  jmp y-- delay [15]   ; 23 × 16 = 368 тактів ≈ 30,7 мкс
  pull noblock         ; беремо відповідь з TX FIFO
  set pins, 1          ; СПОЧАТКУ виставляємо високий рівень
  set pindirs, 1       ; ПОТІМ вмикаємо вихід
  set y, 20
tx:
  out pins, 1 [30]     ; 21 біт по 32 такти
  jmp y-- tx
  set pins, 1          ; повертаємо лінію вгору
  set pindirs, 0       ; ніжка знову вхід
```

Чому порядок важливий: якщо спершу ввімкнути вихід, а потім виставити рівень, на лінії може проскочити короткий провал донизу. FC сприйме його як початок відповіді.

### 6.3. Підготувати відповідь заздалегідь

CPU кладе відповідь у TX FIFO **до** того, як прийде кадр. Справжні ESC роблять так само: віддають останнє виміряне значення.

```rust
sm.tx().push(encode_reply(0x0FFF));          // перед першим кадром: «мотор стоїть»
loop {
    let frame = (!sm.rx().wait_pull().await & 0xFFFF) as u16;
    // ...
    let _ = sm.tx().try_push(encode_reply(0x05F4)); // відповідь для наступного кадру
}
```

Якщо FIFO виявиться порожнім, `pull noblock` візьме значення з X, а там після циклу `0xFFFFFFFF`. Лінія просто залишиться високою, і FC зарахує пропущену телеметрію, але нічого не зламається.

**Перевірка на аналізаторі:**

| Що міряємо | Очікуване значення |
|---|---|
| Пауза між кінцем кадру і першим спадом відповіді | 25–35 мкс |
| Тривалість біта відповіді | 2,667 мкс |
| Тривалість відповіді | ≈56 мкс |
| Лінія після відповіді | висока, без «хвостів» |

Порівняйте форму відповіді з очікуваними рівнями з кроку 5. Для `0x5F4` на аналізаторі має бути 21 біт по 2,667 мкс, біт у біт:

```
0 1100110101010010 1101
^ старт-біт (лінія вниз)
```

### 6.4. Повна PIO-програма

Прийом із кроку 4 і передача з кроку 6.2 разом:

```
.wrap_target
idle:
  set y, 31
idle_loop:
  jmp pin still_high   ; лінія висока — рахуємо далі
  jmp idle             ; впала — починаємо відлік спочатку
still_high:
  jmp y-- idle_loop    ; 32 × 2 такти ≈ 5,3 мкс тиші
  set x, 15
bit:
  wait 0 pin 0 [19]    ; спадаючий фронт + чекаємо до середини біта
  in pins, 1           ; читаємо рівень
  wait 1 pin 0         ; чекаємо, поки лінія знову підніметься
  jmp x-- bit          ; після виходу X = 0xFFFFFFFF
  set y, 22
delay:
  jmp y-- delay [15]   ; пауза ≈ 30 мкс
  pull noblock         ; відповідь з TX FIFO (або X, якщо FIFO порожнє)
  set pins, 1          ; СПОЧАТКУ рівень
  set pindirs, 1       ; ПОТІМ вихід
  set y, 20
tx:
  out pins, 1 [30]     ; 21 біт по 32 такти
  jmp y-- tx
  set pins, 1          ; лінія вгору
  set pindirs, 0       ; ніжка знову вхід
.wrap
```

Явного `push` у програмі немає: прийнятий кадр кладе в RX FIFO autopush після 16-го біта. Тому `shift_in` має лишатися таким, як зараз:

```rust
cfg.shift_in = ShiftConfig {
    auto_fill: true,
    direction: ShiftDirection::Left,
    threshold: 16,
};
```

Явний `push` додав би зайвий такт до паузи. І autopush, і `push` зупиняють стейт-машину, якщо RX FIFO заповнений, тому CPU має встигати забирати кадри: інакше PIO застрягне посеред обміну і пропустить відповідь.

## Крок 8. Етап C — справжнє значення eRPM

Тепер замість константи передаємо реальний (або імітований) період обертання.

Формат 12 біт: 3 біти експоненти `e` і 9 біт мантиси `m`. Період електричного оберту в мікросекундах = `m << e`.

```rust
/// Кодує період електричного оберту (мкс) у 12-бітний формат DShot.
fn encode_period(period_us: u32) -> u16 {
    if period_us == 0 {
        return 0x0FFF;
    }
    let mut m = period_us;
    let mut e = 0;
    while m > 0x1FF {
        m >>= 1;
        e += 1;
    }
    if e > 7 {
        return 0x0FFF; // занадто повільно — вважаємо, що мотор стоїть
    }
    ((e << 9) | m) as u16
}
```

Приклади розрахунку (період = 60 000 000 / eRPM):

| eRPM | Період, мкс | e | m | e12 |
|---|---|---|---|---|
| 10 000 | 6000 | 4 | 375 | `0x977` |
| 30 000 | 2000 | 2 | 500 | `0x5F4` |
| стоїть | — | 7 | 511 | `0xFFF` |

Для тестового стенда можна, наприклад, перетворювати отриманий газ у «вигадані» оберти:

```rust
let throttle = frame >> 5;              // 0..2047
let erpm = 1000 + throttle as u32 * 20; // проста лінійна модель
let period = 60_000_000 / erpm;
let _ = sm.tx().try_push(encode_reply(encode_period(period)));
```

**Перевірка:** при зміні газу у вкладці «Motors» змінюються оберти.

## Крок 9. Крайові випадки

Перевірте поведінку стенда в незручних ситуаціях:

1. **Увімкнення посеред кадру.** RP2040 вмикається, коли FC уже шле кадри. Цикл `idle` має дочекатися паузи і почати з початку кадру.
2. **FC перестав слати кадри.** PIO має просто чекати, не виходячи на лінію.
3. **Кадр з поганою CRC.** Чи відповідати на нього? Справжні ESC зазвичай не відповідають. Для цього знадобиться окремий сигнал від CPU до PIO — це можна зробити пізніше.
4. **Спеціальні команди DShot** (газ 0–47, наприклад, запит версії або біп). Поки що їх достатньо просто логувати.

## Крок 10 (необов'язково). Повернути debug-ніжку

Група SET охоплює лише суміжні ніжки, а GPIO3 не стоїть поруч із GPIO0 (група з base = GPIO0 і count = 4 зачепила б ще й GPIO1–2), тому debug-вихід на GPIO3 довелося прибрати. Його можна повернути через **side-set**:

```rust
cfg.use_program(&loaded, &[&debug_pin]); // side-set на GPIO3
```

А в програмі додати `side 1` / `side 0` до потрібних інструкцій, наприклад:

```
  in pins, 1   side 1
```

Майте на увазі: side-set забирає біти з поля затримки, тому максимальна затримка `[n]` зменшиться. Затримки `[30]` і `[19]` доведеться розбити на кілька інструкцій.
