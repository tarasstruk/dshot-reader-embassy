# Розширена телеметрія DShot (EDT)

Що таке EDT, за якими правилами його вмикають і вимикають, як ми це реалізували (коміти `090c6a1`, `9628bdc` і надсилання температури та струму) і чого чекати на стенді.

Специфікація: [bird-sanctuary/extended-dshot-telemetry](https://github.com/bird-sanctuary/extended-dshot-telemetry).

> **Коротко.**
> - EDT передає температуру, струм, напругу тощо в тій самій відповіді, де зазвичай іде період оберту. Окремого проводу не треба.
> - FC вмикає EDT командою DShot 13, надісланою щонайменше 6 разів поспіль. ESC відповідає один раз кадром версії. Команда 14 так само вимикає EDT.
> - У нас готові кодування (`encode_temperature`, `encode_current`, `decode_telemetry`) і ввімкнення та вимкнення (`EdtSwitch`, поле `edt` у рядку USB).
> - З `edt=1` кожна 64-та відповідь несе замість періоду температуру (стала 42 °C) або струм (0–20 А за газом), по черзі.

## 1. Формат

### 1.1. Де живе EDT

Відповідь ESC несе 12-бітне значення `e12` (плюс CRC, GCR і NRZI, як і раніше; див. `reply-waveform-0x5F4.md`). Для періоду оберту це:

```
eee m mmmm mmmm      період = m << e  (мкс)
```

`encode_period` ділить період навпіл, доки мантиса не вміститься в 9 біт, тобто доки вона не стане 256…511. Отже, при `e` > 0 старший біт мантиси (біт 8) у періоду **завжди 1**. Значення з `e` > 0 і бітом 8 = 0 ніколи не трапляються як період, і EDT займає саме їх:

```
ppp 0 vvvv vvvv      тип = ppp0 (біти 11..8), значення = біти 7..0
```

Правило розрізнення: якщо 4-бітний тип (біти 11..8) дорівнює 0 **або** біт 8 = 1, це період, інакше — EDT.

### 1.2. Типи

| Біти 11..8 | Тип | Одиниці | У кодеку |
|---|---|---|---|
| `0010` (0x2) | температура | °C, 0–255 | `encode_temperature`, `Telemetry::Temperature` |
| `0100` (0x4) | напруга | 0,25 В, 0–63,75 В | `Telemetry::Other { kind: 0x4 }` |
| `0110` (0x6) | струм | А, 0–255 | `encode_current`, `Telemetry::Current` |
| `1000` (0x8) | debug 1 | — | `Telemetry::Other` |
| `1010` (0xA) | debug 2 | — | `Telemetry::Other` |
| `1100` (0xC) | stress level | 0–255 | `Telemetry::Other` |
| `1110` (0xE) | status; також кадр версії і «EDT вимкнено» | прапорці | `Telemetry::Other` |

Приклади: 50 °C → `0x232`, 17 А → `0x611`, 16,75 В (67 кроків) → `0x443`.

CRC, GCR і NRZI для EDT ті самі, що й для періоду: `encode_reply` байдуже, що означає `e12`.

## 2. Як EDT вмикають і вимикають

### 2.1. Команди DShot

Окремого каналу для команд у DShot немає. Команда — це звичайний кадр, у якому в полі газу стоїть значення 1…47 (`Frame::is_command()`). Для EDT потрібні дві:

| Команда | Кадр | Що робить ESC | Відповідь ESC (один раз) |
|---|---|---|---|
| 13 — `EXTENDED_TELEMETRY_ENABLE` | `throttle = 13` | вмикає EDT | кадр версії `1110 vvvv vvvv` (`0xE..`) |
| 14 — `EXTENDED_TELEMETRY_DISABLE` | `throttle = 14` | вимикає EDT | `1110 1111 1111` (`0xEFF`) |

### 2.2. Чому 6 разів поспіль

Одиночний кадр може бути зіпсований завадою так, що CRC випадково зійдеться. Для газу це не страшно: наступний кадр через 250 мкс усе виправить. Але команди, що змінюють стан ESC надовго (напрямок обертання 7 і 8, збереження налаштувань 12, EDT 13 і 14), виконуються лише після кількох **однакових кадрів поспіль**. Кадр з іншим значенням між повторами скидає лічильник. Для EDT специфікація вимагає щонайменше 6 повторів. Ймовірність, що завада 6 разів поспіль дасть ту саму валідну команду, практично нульова.

Наскільки відомо з коду Betaflight (з пам'яті, на нашій версії не перевірено), такі команди він надсилає **10 разів поспіль** і зі встановленим бітом T.

## 3. Реалізація

### 3.1. Кодек (`dshot-codec`)

| Що | Опис |
|---|---|
| `enum Telemetry { Period(u32), Temperature(u8), Current(u8), Other { kind, value } }` | що несе `e12` |
| `decode_telemetry(e12) -> Telemetry` | розбирає `e12`, як FC: за правилом з 1.1 |
| `encode_temperature(celsius: u8) -> u16` | `0x200 \| celsius` |
| `encode_current(amps: u8) -> u16` | `0x600 \| amps` |
| `encode_edt_version(v: u8) -> u16` | `0xE00 \| v` |
| `CMD_EDT_ENABLE = 13`, `CMD_EDT_DISABLE = 14` | команди |
| `COMMAND_REPEATS = 6` | скільки однакових кадрів поспіль потрібно |
| `EDT_VERSION = 2` | версія, яку ми повідомляємо (за номером специфікації v2) |
| `E12_EDT_DISABLED = 0xEFF` | відповідь на вимкнення |
| `struct EdtSwitch` | стан «EDT увімкнено» і лічильник повторів |

**Правила `EdtSwitch::on_frame(frame)`:**

1. Якщо газ у кадрі такий самий, як у попередньому, лічильник +1. Інакше лічильник = 1, і запам'ятовується нове значення.
2. Команда спрацьовує на **рівно 6-му** кадрі поспіль:
   - `13` → EDT увімкнено, повертає `Some(0xE02)`;
   - `14` → EDT вимкнено, повертає `Some(0xEFF)`;
   - будь-яке інше значення → нічого.
3. 7-й, 8-й і далі повтори нічого не роблять. Betaflight шле більше 6, і без цього правила кадр версії йшов би кілька разів.
4. Повторне ввімкнення вже ввімкненого EDT (новий ряд з шести `13` після іншого кадру) знову повертає кадр версії. Специфікація цього не забороняє, а FC так дізнається, що ESC його почув.

**Тести** (`cargo test-codec`):

| Тест | Що перевіряє |
|---|---|
| `edt_examples` | `0x232` = 50 °C, `0x611` = 17 А, `0x443` — напруга, `0xE02` — версія |
| `edt_roundtrip_all_values` | усі 0…255 для температури і струму, також через `encode_reply` / `decode_reply` |
| `period_is_never_taken_for_edt` | жоден результат `encode_period` (0…65 536 мкс і «мотор стоїть») не розпізнається як EDT |
| `edt_switch_needs_six_in_a_row` | 5 повторів замало; 6-й вмикає і дає `0xE02` один раз; 10 зайвих повторів і кадри газу нічого не змінюють; шість `14` вимикають і дають `0xEFF` |
| `edt_switch_count_restarts_on_other_frame` | кадр «мотор стоп» між командами скидає лічильник |
| `edt_control_frames_are_edt` | кадри версії і «вимкнено» розпізнаються як EDT, а не як період |

### 3.2. Прошивка (`src/main.rs`)

- Задача PIO тримає один `EdtSwitch`.
- Кожен кадр з **добрим CRC** іде в `edt.on_frame(frame)`. Кадри з поганою CRC туди не потрапляють: лічильник вони не скидають, але й не збільшують.
- Якщо `on_frame` повернув кадр (`0xE02` або `0xEFF`), він іде в TX FIFO **один раз замість періоду**. Далі знову йде період за моделлю етапу C.
- Одноразовий кадр зберігається окремо від звичайної відповіді. Тож він не загубиться, навіть якщо задача за раз забрала з RX кілька кадрів (`docs/rx-overflow-plan.md`, крок 2).
- **Біт T не перевіряється**: команда спрацьовує з T = 0 і з T = 1. Чи вимагати T = 1, вирішимо, коли побачимо, що шле наш FC.
- **З увімкненим EDT кожна `EDT_EVERY` = 64-та відповідь** несе замість періоду значення EDT, по черзі: температура, струм, температура, … Деталі — у 3.4.
- У рядку USB нове поле `edt=0/1` — стан `EdtSwitch`:

  ```
  7D05 thr=1000 T=0 cmd=0 n=12345 bad=0 txf=0 late=0 gap=251 edt=1
  ```

### 3.3. Коли саме FC отримає кадр версії

Відповідь у TX FIFO завжди на кадр наперед: відповідь, порахована після кадру N, йде на лінію як відповідь на кадр N+1. Тому:

| Кадр FC | Відповідь на лінії |
|---|---|
| 1…6-й кадр `13` | період (для команд — «мотор стоїть», `0xFFF`) |
| 7-й кадр `13` | **`0xE02`** — кадр версії |
| 8-й і далі | знову `0xFFF` (команда, газ < 48) |

Betaflight шле 10 повторів, тож кадр версії приходить ще посеред серії команд.

### 3.4. Температура і струм

Як і eRPM на етапі C, значення EDT — іграшкові: мотора немає, вимірювати нічого.

| Константа | Значення | Що означає |
|---|---|---|
| `EDT_EVERY` | 64 | кожна 64-та відповідь — EDT, решта — період |
| `EDT_TEMPERATURE_C` | 42 | температура, °C, стала |
| `EDT_CURRENT_MAX_A` | 20 | струм на повному газі, А |

**Струм** (`current_for`): 0 А для команд (газ 0…47), далі лінійно від 0 А на газі 48 до 20 А на газі 2047, з відкиданням дробу:

| Газ | Струм | `e12` |
|---|---|---|
| 0…47 (команди) | 0 А | `0x600` |
| 48 | 0 А | `0x600` |
| 1000 | 9 А (9,5) | `0x609` |
| 1500 | 14 А (14,5) | `0x60E` |
| 2047 | 20 А | `0x614` |

Температура: `0x22A` (42 °C) завжди.

**Частота.** Кадр приходить кожні 250 мкс, тож одне значення EDT іде кожні 64 × 250 мкс = 16 мс, а кожен тип окремо — кожні ≈ 32 мс (≈ 30 разів на секунду). Справжні ESC теж вставляють EDT між відповідями з періодом. FC при цьому втрачає 1/64 відповідей з eRPM (≈ 1,6 %): у ці моменти RPM-фільтр бере попереднє значення.

**Лічильник рахує відповіді, а не кадри.** Якщо задача за раз забрала з RX кілька кадрів (`docs/rx-overflow-plan.md`), лічильник зростає на 1. З release-збіркою задача прокидається на кожен кадр, тож різниці немає.

**Порядок з одноразовими кадрами.** Кадр версії або `0xEFF` має перевагу: у той раз EDT-значення не йде, і лічильник не зростає. Струм береться з останнього кадру з добрим CRC.

## 4. Чого ще немає

1. **Значення справжні лише за формою.** Температура стала, струм — модель від газу (3.4). Справжню температуру можна було б брати з вбудованого датчика RP2040 (АЦП, канал 4).
2. **Напруга, stress і status не надсилаються**, хоча кодек їх розпізнає (`Telemetry::Other`).
3. **Значення версії.** `2` взято з номера специфікації. Яке число шлють Bluejay чи BLHeli_32, не перевірено.
4. **Біт T** — див. 3.2.
5. **Після перезавантаження RP2040 EDT вимкнено**, доки FC знову не надішле команду 13.

## 5. Чого чекати на стенді

### 5.1. Налаштування Betaflight

```
set dshot_edt = ON
save
```

`save` перезавантажує FC. Назва параметра `dshot_edt` — з пам'яті; якщо CLI її не знає, перевірте `get edt` або `get dshot`.

Коли саме Betaflight надсилає команду 13, не перевірено. Найімовірніше — при старті, коли вмикаються виходи моторів, і, можливо, повторно після кожного disarm.

### 5.2. Що побачити

| Де | Що | Очікується |
|---|---|---|
| `tio` | поле `edt` | `edt=0` до команди; `edt=1` після неї, і тримається. Після перезавантаження RP2040 (`n` скидається) — знову `edt=0`, доки FC не надішле команду 13 ще раз |
| `tio` | кадри команди | серія з ≈ 10 кадрів `thr=13` триває ≈ 2,5 мс, тож рядок раз на 0,5 с її, найімовірніше, **не покаже**. Достатньо побачити `edt=1` |
| `tio` | `bad`, `txf`, `late` | без змін: 0 / 0 / ≈ 0 |
| `dshot_telemetry_info` | колонка Type мотора 4 | `RT-C-` (eRPM, температура, струм) замість `R----` |
| `dshot_telemetry_info` | TEMP, CURR | 42 і струм за таблицею з 3.4: 0 при газі 0, 9 при газі 1000 (`motor 3 1477`), 20 при газі 2047 (`motor 3 2000`). Одиниці CURR у Betaflight — з пам'яті, можуть бути інші |
| `dshot_telemetry_info` | eRPM / Invalid | як на етапі C, Invalid 0 %. Кадри EDT не мають збільшувати Invalid: CRC у них правильний. Якщо Invalid ≈ 1,6 % (1/64), Betaflight вважає кадри EDT поганими — тоді EDT у ньому, найімовірніше, не ввімкнено |
| осцилограф | відповідь на 7-й кадр `13` | рівні `encode_reply(0xE02)` замість `0xFFF`. Спіймати її вручну важко: потрібен запуск по першому кадру після паузи і щастя |

### 5.3. Якщо `edt` лишається 0

| Причина | Як перевірити |
|---|---|
| Betaflight не надсилає команду 13 (параметр не ввімкнено або не збережено) | `get dshot_edt`; перезавантажити FC |
| Betaflight надсилає 13 менше 6 разів поспіль або вперемішку з іншими кадрами | на осцилографі: серія кадрів з однаковим газом 13 після старту FC |
| Betaflight вимагає від ESC чогось ще | Type і Invalid у `dshot_telemetry_info`; порівняти зі справжнім ESC з EDT (Bluejay) |
