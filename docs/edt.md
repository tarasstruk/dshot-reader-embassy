# Розширена телеметрія DShot (EDT)

Що таке EDT, за якими правилами його вмикають і вимикають, як ми це реалізували (коміти `090c6a1`, `9628bdc`, надсилання температури та струму, а в день 005 — `15f6f56`, `1d74b22`, `e023a38`: напруга, status, debug, крейт `esc-emu`) і чого чекати на стенді.

Специфікація: [bird-sanctuary/extended-dshot-telemetry](https://github.com/bird-sanctuary/extended-dshot-telemetry).

> **Коротко.**
> - EDT передає температуру, струм, напругу тощо в тій самій відповіді, де зазвичай іде період оберту. Окремого проводу не треба.
> - FC вмикає EDT командою DShot 13, надісланою щонайменше 6 разів поспіль. ESC відповідає один раз кадром версії. Команда 14 так само вимикає EDT.
> - У кодеку — кодування всіх типів, які ми шлемо (`encode_temperature`, `encode_voltage`, `encode_current`, `encode_status`, `encode_debug1`, `encode_debug2`), розбір `decode_telemetry` і ввімкнення та вимкнення (`EdtSwitch`). Поле `edt` у рядку USB показує стан.
> - Логіка відповіді — у крейті `esc-emu` (тести на ПК). З `edt=1` кожна **32-га** відповідь несе замість періоду одне значення EDT, по колу: температура → напруга → струм → status → debug 1 → debug 2. Температура і напруга залежать від обертів, струм — від газу (3.4).
> - **Betaflight надсилає команду 13 лише при озброєнні**, а стендовий FC озброїти не можна. Тому на стенді FC стоїть у `dshot_edt = FORCE` (розбирає EDT без команди), а прошивка шле EDT з самого старту (`EDT_AT_START = true`). Перевірено на стенді: `reports/004-with-probe-rs/edt-details.md`.

## 1. Формат

### 1.1. Де живе EDT

Відповідь ESC несе 12-бітне значення `e12` (плюс CRC, GCR і NRZI, як і раніше; див. `reply-waveform-0x5F4.md`). Для періоду оберту це:

```
eee m mmmm mmmm      період = m << e  (мкс)
```

`encode_period` ділить період навпіл, доки мантиса не вміститься в 9 біт, тобто доки вона не стане 256…511. Отже, при `e` > 0 старший біт мантиси (біт 8) у періоду **завжди 1**. Значення з `e` > 0 і бітом 8 = 0 ніколи не трапляються як період, і EDT займає саме їх:

```
ppp 0 vvvv vvvv      тип = ppp0 (біти 11..8), значення = біти 7..0
```

Правило розрізнення: якщо 4-бітний тип (біти 11..8) дорівнює 0 **або** біт 8 = 1, це період, інакше — EDT.

### 1.2. Типи

| Біти 11..8 | Тип | Одиниці | У кодеку |
|---|---|---|---|
| `0010` (0x2) | температура | °C, 0–255 | `encode_temperature`, `Telemetry::Temperature` |
| `0100` (0x4) | напруга | 0,25 В, 0–63,75 В | `encode_voltage`, `Telemetry::Voltage` |
| `0110` (0x6) | струм | А, 0–255 | `encode_current`, `Telemetry::Current` |
| `1000` (0x8) | debug 1 | 0–255, на розсуд ESC | `encode_debug1`, `Telemetry::Debug1` |
| `1010` (0xA) | debug 2 | 0–255, на розсуд ESC | `encode_debug2`, `Telemetry::Debug2` |
| `1100` (0xC) | stress level | 0–255 | `Telemetry::Other` (не шлемо) |
| `1110` (0xE) | status; також кадр версії і «EDT вимкнено» | прапорці | `encode_status`, `Telemetry::Status` |

Приклади: 50 °C → `0x232`, 17 А → `0x611`, 16,75 В (67 кроків) → `0x443`, 15,25 В (61 крок) → `0x43D`.

**Status** (`struct Status`): біт 7 — alert, біт 6 — warning, біт 5 — error, біти 3..0 — max stress (0–15), біт 4 не використовується. Приклад: warning + stress 11 → `0xE4B`. Кадр версії (`0xE02`) і «EDT вимкнено» (`0xEFF`) мають той самий тип `0xE`; FC відрізняє їх лише за контекстом — як відповідь на команду 13 чи 14. Тому `decode_telemetry` розбирає їх як `Telemetry::Status`.

CRC, GCR і NRZI для EDT ті самі, що й для періоду: `encode_reply` байдуже, що означає `e12`.

## 2. Як EDT вмикають і вимикають

### 2.1. Команди DShot

Окремого каналу для команд у DShot немає. Команда — це звичайний кадр, у якому в полі газу стоїть значення 1…47 (`Frame::is_command()`). Для EDT потрібні дві:

| Команда | Кадр | Що робить ESC | Відповідь ESC (один раз) |
|---|---|---|---|
| 13 — `EXTENDED_TELEMETRY_ENABLE` | `throttle = 13` | вмикає EDT | кадр версії `1110 vvvv vvvv` (`0xE..`) |
| 14 — `EXTENDED_TELEMETRY_DISABLE` | `throttle = 14` | вимикає EDT | `1110 1111 1111` (`0xEFF`) |

### 2.2. Чому 6 разів поспіль

Одиночний кадр може бути зіпсований завадою так, що CRC випадково зійдеться. Для газу це не страшно: наступний кадр через 250 мкс усе виправить. Але команди, що змінюють стан ESC надовго (напрямок обертання 7 і 8, збереження налаштувань 12, EDT 13 і 14), виконуються лише після кількох **однакових кадрів поспіль**. Кадр з іншим значенням між повторами скидає лічильник. Для EDT специфікація вимагає щонайменше 6 повторів. Ймовірність, що завада 6 разів поспіль дасть ту саму валідну команду, практично нульова.

У коді Betaflight (`dshot_command.c`) команди 13 і 14 надсилаються **10 разів** з паузою 1 мс (`DSHOT_COMMAND_DELAY_US`); на час паузи FC кадрів не шле взагалі, тож для ESC повтори йдуть поспіль.

### 2.3. Коли Betaflight вмикає EDT

| `dshot_edt` | Чи шле FC команду 13 | Як FC розбирає відповідь |
|---|---|---|
| `OFF` | ні | лише період |
| `ON` | **лише при озброєнні** (у `dshot.c` біля розбору кадру версії коментар «during arming») | EDT — лише для мотора, від якого вже прийшов якийсь тип EDT |
| `FORCE` | ні | EDT завжди (`edtAlwaysDecode`), без обміну командою |

Стендовий FC озброїти не можна (немає приймача, немає телеметрії з моторів 1–3), тому з `ON` команда 13 не приходить ніколи. Це підтвердив лог RP2040: після перезавантаження FC з `dshot_edt = ON` не прийшло жодної команди 1…47 (`reports/004-with-probe-rs/edt-details.md`).

## 3. Реалізація

### 3.1. Кодек (`dshot-codec`)

| Що | Опис |
|---|---|
| `enum Telemetry { Period(u32), Temperature(u8), Voltage(u8), Current(u8), Debug1(u8), Debug2(u8), Status(Status), Other { kind, value } }` | що несе `e12` |
| `struct Status { alert, warning, error, max_stress }` | прапорці і max stress |
| `decode_telemetry(e12) -> Telemetry` | розбирає `e12`, як FC: за правилом з 1.1 |
| `encode_temperature(celsius: u8) -> u16` | `0x200 \| celsius` |
| `encode_voltage(quarter_volts: u8) -> u16` | `0x400 \| кроки по 0,25 В` |
| `encode_current(amps: u8) -> u16` | `0x600 \| amps` |
| `encode_debug1(v: u8)`, `encode_debug2(v: u8)` | `0x800 \| v`, `0xA00 \| v` |
| `encode_status(status: Status) -> u16` | `0xE00 \| прапорці \| max stress` |
| `encode_edt_version(v: u8) -> u16` | `0xE00 \| v` |
| `CMD_EDT_ENABLE = 13`, `CMD_EDT_DISABLE = 14` | команди |
| `COMMAND_REPEATS = 6` | скільки однакових кадрів поспіль потрібно |
| `EDT_VERSION = 2` | версія, яку ми повідомляємо (за номером специфікації v2) |
| `E12_EDT_DISABLED = 0xEFF` | відповідь на вимкнення |
| `struct EdtSwitch` | стан «EDT увімкнено» і лічильник повторів |

**Правила `EdtSwitch::on_frame(frame)`:**

1. Якщо газ у кадрі такий самий, як у попередньому, лічильник +1. Інакше лічильник = 1, і запам'ятовується нове значення.
2. Команда спрацьовує на **рівно 6-му** кадрі поспіль:
   - `13` → EDT увімкнено, повертає `Some(0xE02)`;
   - `14` → EDT вимкнено, повертає `Some(0xEFF)`;
   - будь-яке інше значення → нічого.
3. 7-й, 8-й і далі повтори нічого не роблять. Betaflight шле більше 6, і без цього правила кадр версії йшов би кілька разів.
4. Повторне ввімкнення вже ввімкненого EDT (новий ряд з шести `13` після іншого кадру) знову повертає кадр версії. Специфікація цього не забороняє, а FC так дізнається, що ESC його почув.

**Тести** (`cargo test-codec`):

| Тест | Що перевіряє |
|---|---|
| `edt_examples` | `0x232` = 50 °C, `0x611` = 17 А, `0x443` / `0x43D` — напруга, debug 1 / 2, stress лишається `Other` |
| `edt_status_examples` | `0xE4B` (warning + stress 11), `0xECE` (warning + alert + stress 14), error, порожній статус |
| `edt_status_roundtrip_all_values` | усі 8 комбінацій прапорців × 16 рівнів stress, також через `encode_reply` / `decode_reply` |
| `edt_roundtrip_all_values` | усі 0…255 для температури, напруги, струму, debug 1 / 2, також через `encode_reply` / `decode_reply` |
| `period_is_never_taken_for_edt` | жоден результат `encode_period` (0…65 536 мкс і «мотор стоїть») не розпізнається як EDT |
| `edt_switch_needs_six_in_a_row` | 5 повторів замало; 6-й вмикає і дає `0xE02` один раз; 10 зайвих повторів і кадри газу нічого не змінюють; шість `14` вимикають і дають `0xEFF` |
| `edt_switch_count_restarts_on_other_frame` | кадр «мотор стоп» між командами скидає лічильник |
| `edt_control_frames_are_edt` | кадри версії і «вимкнено» розпізнаються як `Status`, а не як період |

### 3.2. Емуляція ESC (`esc-emu`) і прошивка (`src/main.rs`)

Логіка відповіді живе в крейті `esc-emu` (`Esc`), прошивка лише передає значення між FIFO PIO і `Esc` (`docs/day-005.md`, 5.1).

- `Esc` тримає один `EdtSwitch`. Прошивка створює його через `Esc::new(EDT_AT_START)`; з `EDT_AT_START = true` (так зараз, константа в `src/main.rs`) EDT увімкнено з самого старту (`EdtSwitch::enabled_at_start()`), без кадру версії; команди 13 і 14 далі працюють як описано. З `false` — вимкнено, і `Esc` чекає команду 13.
- Кожне значення з RX FIFO іде в `Esc::on_raw(raw)`. Кадр з **добрим CRC** іде в `EdtSwitch::on_frame`; кадри з поганою CRC туди не потрапляють: лічильник вони не скидають, але й не збільшують.
- Якщо `on_frame` повернув кадр (`0xE02` або `0xEFF`), `on_raw` віддає його в `Received::edt_event` (прошивка пише лог defmt), а `Esc::next_reply` шле його в TX FIFO **один раз замість періоду**. Далі знову йде період за моделлю етапу C.
- Одноразовий кадр зберігається окремо від звичайної відповіді. Тож він не загубиться, навіть якщо задача за раз забрала з RX кілька кадрів (`docs/rx-overflow-plan.md`, крок 2).
- **Біт T не перевіряється**: команда спрацьовує з T = 0 і з T = 1.
- **З увімкненим EDT кожна `EDT_EVERY` = 32-га відповідь** несе замість періоду одне значення EDT, по колу з шести типів. Деталі — у 3.4.
- `Esc::next_reply(counters)` отримує від прошивки `Counters { bad, late }` — їхні молодші байти йдуть як debug 1 і debug 2.
- Тести `esc-emu`: `cargo test-esc-emu` (`docs/day-005.md`, 5.1).
- У рядку USB поле `edt=0/1` — стан `EdtSwitch`:

  ```
  7D05 thr=1000 T=0 cmd=0 n=12345 bad=0 txf=0 late=0 gap=251 edt=1
  ```

### 3.3. Коли саме FC отримає кадр версії

Відповідь у TX FIFO завжди на кадр наперед: відповідь, порахована після кадру N, йде на лінію як відповідь на кадр N+1. Тому:

| Кадр FC | Відповідь на лінії |
|---|---|
| 1…6-й кадр `13` | період (для команд — «мотор стоїть», `0xFFF`) |
| 7-й кадр `13` | **`0xE02`** — кадр версії |
| 8-й і далі | знову `0xFFF` (команда, газ < 48) |

Betaflight шле 10 повторів, тож кадр версії приходить ще посеред серії команд.

### 3.4. Значення EDT (`esc-emu`)

Як і eRPM на етапі C, значення EDT — іграшкові: мотора немає, вимірювати нічого. Усе, крім струму і debug, рахується від **eRPM моделі** (до округлення e12): eRPM = 1000 + газ × 20, і 0 для команд (газ 0…47). Цілочисельно, з відкиданням дробу. Обґрунтування — `docs/day-005.md`.

| Тип | Функція | Формула | Константи |
|---|---|---|---|
| температура, °C | `temperature_for` | 25 + 60 × eRPM / 42 000 | `TEMP_IDLE_C = 25`, `TEMP_FULL_C = 85`, `ERPM_FULL = 42_000` |
| напруга, кроки по 0,25 В | `voltage_for` | (16 800 − 2 800 × eRPM / 42 000) / 250, у мВ | `VOLT_IDLE_MV = 16_800`, `VOLT_FULL_MV = 14_000`, `VOLT_STEP_MV = 250` |
| струм, А | `current_for` | (газ − 48) × 20 / 1999; 0 для команд | `EDT_CURRENT_MAX_A = 20` |
| status | `status_for` | alert при T ≥ 80, warning при T ≥ 70, error — ніколи; max stress = (T − 25) × 15 / 60 | `TEMP_WARNING_C = 70`, `TEMP_ALERT_C = 80` |
| debug 1 | — | молодший байт `bad` (кадри з поганим CRC) | — |
| debug 2 | — | молодший байт `late` (пізні пробудження задачі PIO) | — |

Очікувані значення (тест `edt_models_table`):

| Газ (`motor 3 …`) | eRPM моделі | TEMP, °C | VCC, В (кроки) | CURR, А | Status |
|---|---|---|---|---|---|
| 0 (1000) | 0 | 25 | 16,75 (67) | 0 | `0x00` |
| 48 (1001) | 1 960 | 27 | 16,50 (66) | 0 | `0x00` |
| 546 (1250) | 11 920 | 42 | 16,00 (64) | 4 | `0x04` (stress 4) |
| 1046 (1500) | 21 920 | 56 | 15,25 (61) | 9 | `0x07` (stress 7) |
| 1546 (1750) | 31 920 | 70 | 14,50 (58) | 14 | `0x4B` — warning, stress 11 |
| 2047 (2000) | 41 940 | 84 | 14,00 (56) | 20 | `0xCE` — warning + alert, stress 14 |

До першого кадру з добрим CRC мотор вважається зупиненим: 25 °C, 16,75 В, 0 А.

**Порядок і частота.** Кожна 32-га відповідь — EDT, по колу:

```
температура → напруга → струм → status → debug 1 → debug 2 → температура → …
```

Кадр приходить кожні 250 мкс, тож одне значення EDT іде кожні 32 × 250 мкс = 8 мс, а кожен тип окремо — кожні 6 × 8 = 48 мс (≈ 20 разів на секунду). Справжні ESC теж вставляють EDT між відповідями з періодом. FC при цьому втрачає 1/32 відповідей з eRPM (≈ 3 %): у ці моменти RPM-фільтр бере попереднє значення.

**Лічильник рахує відповіді, а не кадри.** Якщо задача за раз забрала з RX кілька кадрів (`docs/rx-overflow-plan.md`), лічильник зростає на 1. З release-збіркою задача прокидається на кожен кадр, тож різниці немає.

**Порядок з одноразовими кадрами.** Кадр версії або `0xEFF` має перевагу: у той раз EDT-значення не йде, і лічильник не зростає. Значення беруться з останнього кадру з добрим CRC.

## 4. Чого ще немає

1. **Значення справжні лише за формою.** Температура, напруга, струм і status — іграшкові моделі (3.4). Справжню температуру можна було б брати з вбудованого датчика RP2040 (АЦП, канал 4).
2. **Stress level (`0xC`) не надсилається**, хоча кодек його розпізнає (`Telemetry::Other`). Max stress іде лише в складі status.
3. **Значення версії.** `2` взято з номера специфікації. Яке число шлють Bluejay чи BLHeli_32, не перевірено.
4. **Біт T** — див. 3.2.
5. **З `EDT_AT_START = false` після перезавантаження RP2040 EDT вимкнено**, доки FC знову не надішле команду 13 — а Betaflight шле її лише при озброєнні.

## 5. Чого чекати на стенді

### 5.1. Налаштування Betaflight

```
set dshot_edt = FORCE
save
```

`save` перезавантажує FC. Значення `FORCE`, бо стендовий FC не озброюється і команду 13 не шле (2.3); прошивка має `EDT_AT_START = true`. Для FC, який озброюється, можна `ON` і `EDT_AT_START = false`.

### 5.2. Що побачити

| Де | Що | Очікується |
|---|---|---|
| `tio` | поле `edt` | `edt=1` одразу після старту RP2040 (`EDT_AT_START = true`) |
| `tio` | `bad`, `txf`, `late` | без змін: 0 / 0 / ≈ 0 |
| `dshot_telemetry_info` | колонка Type мотора 4 | R, T, V, C і ще літери для status / debug — точні літери перевірити на стенді (з лише температурою і струмом було `RT-C-`) |
| `dshot_telemetry_info` | TEMP, VCC, CURR, ST/EV, DBG1, DBG2 | за таблицею з 3.4; як Betaflight показує status у ST/EV — перевірити |
| `dshot_telemetry_info` | eRPM / Invalid | як на етапі C, Invalid 0 %. Кадри EDT не мають збільшувати Invalid: CRC у них правильний. Якщо Invalid ≈ 3 % (1/32), Betaflight вважає кадри EDT поганими — тоді EDT у ньому, найімовірніше, не ввімкнено |

### 5.3. Якщо TEMP, VCC і CURR лишаються 0

| Причина | Як перевірити |
|---|---|
| у FC `dshot_edt = ON` (а не `FORCE`), і FC не озброєний | `get dshot_edt` |
| у прошивці `EDT_AT_START = false`, а FC не шле команду 13 | рядок `tio`: `edt=0` |
| Invalid ≈ 3 % (1/32) | FC не розбирає EDT: див. перший рядок |
