# День 005 — план: більше телеметрії EDT

**Дата плану:** 2026-10-18. **Гілка:** `with-probe-rs`.

**Стан на початок:** коміт `8ea084a`. EDT працює на стенді (FC `dshot_edt = FORCE`, прошивка `EDT_AT_START = true`): температура стала 42 °C, струм 0–20 А за газом (`reports/004-with-probe-rs/edt-details.md`).

> **Мета дня.**
> 1. Температура і напруга залежать від обертів: температура росте, напруга просідає.
> 2. Нові типи EDT: **Status** (попередження про перегрів) і **Debug 1 / Debug 2** (лічильники RP2040). Тоді в `dshot_telemetry_info` заповнені всі колонки, крім DBG3 (stress).
> 3. Логіка відповіді ESC виноситься з `src/main.rs` в окремий крейт `esc-emu`, щоб моделі й чергування EDT перевірялися тестами на ПК.

## 1. Рішення

| Питання | Рішення |
|---|---|
| Які типи EDT додаємо | Voltage (`0x4`), Status (`0xE`), Debug 1 (`0x8`), Debug 2 (`0xA`). Stress level (`0xC`) — ні |
| Температура | лінійно від eRPM: **25 °C** на 0 → **85 °C** на 42 000 eRPM |
| Напруга | лінійне просідання від eRPM: **16,8 В** на 0 → **14,0 В** на 42 000 eRPM. Не буквально «обернено пропорційно»: формула k / оберти дає нескінченність на 0 обертах |
| Струм | без змін: 0 А на газі 48 → 20 А на газі 2047 |
| Status | warning при температурі ≥ 70 °C, alert при ≥ 80 °C, error — ніколи; «max stress» (0–15) лінійно від температури |
| Debug 1 / Debug 2 | молодший байт лічильників `bad` і `late` |
| Частота EDT | кожна **32-га** відповідь (було 64-та) |
| Де логіка ESC | окремий крейт `esc-emu` з власними тестами на ПК |

Пороги Status (70 / 80 °C) обрано так, щоб на прогоні по всьому діапазону газу побачити і warning, і alert. Їх легко змінити константами.

## 2. Формули

Усі значення рахуються від **eRPM моделі** (до округлення e12): eRPM = 1000 + газ × 20 для газу 48…2047, і 0 для команд (газ 0…47). Цілочисельно, з відкиданням дробу.

| Величина | Формула | Константи |
|---|---|---|
| температура, °C | 25 + 60 × eRPM / 42 000 | `TEMP_IDLE_C = 25`, `TEMP_FULL_C = 85`, `ERPM_FULL = 42_000` |
| напруга, кроки по 0,25 В | (16 800 − 2 800 × eRPM / 42 000) / 250, у мВ | `VOLT_IDLE_MV = 16_800`, `VOLT_FULL_MV = 14_000` |
| струм, А | (газ − 48) × 20 / 1999; 0 для команд | без змін |
| max stress (0–15) | (температура − 25) × 15 / 60 | — |
| Status | біт 7 alert (T ≥ 80), біт 6 warning (T ≥ 70), біт 5 error (0), біти 3–0 max stress | `TEMP_WARNING_C = 70`, `TEMP_ALERT_C = 80` |
| Debug 1 | `bad` & 0xFF | — |
| Debug 2 | `late` & 0xFF | — |

### 2.1. Очікувані значення

| Газ (`motor 3 …`) | eRPM моделі | TEMP, °C | VCC, В (кроки) | CURR, А | max stress | Status |
|---|---|---|---|---|---|---|
| 0 (1000) | 0 | 25 | 16,75 (67) | 0 | 0 | `0x00` |
| 48 (1001) | 1 960 | 27 | 16,50 (66) | 0 | 0 | `0x00` |
| 546 (1250) | 11 920 | 42 | 16,00 (64) | 4 | 4 | `0x04` |
| 1046 (1500) | 21 920 | 56 | 15,25 (61) | 9 | 7 | `0x07` |
| 1546 (1750) | 31 920 | 70 | 14,50 (58) | 14 | 11 | `0x4B` — warning |
| 2047 (2000) | 41 940 | 84 | 14,00 (56) | 20 | 14 | `0xCE` — warning + alert |

16,8 В у кроки по 0,25 В не ділиться без остачі: 67 кроків = 16,75 В.

## 3. Формати кадрів (`e12`)

| Тип | `e12` | Приклад |
|---|---|---|
| температура | `0x200 \| °C` | 56 °C → `0x238` |
| напруга | `0x400 \| кроки` | 15,25 В → 61 → `0x43D` |
| струм | `0x600 \| А` | 9 А → `0x609` |
| debug 1 | `0x800 \| значення` | — |
| debug 2 | `0xA00 \| значення` | — |
| status | `0xE00 \| прапорці` | warning + stress 11 → `0xE4B` |

**Застереження щодо Status.** Тип `0xE` той самий, що в кадрі версії (`0xE02`) і в «EDT вимкнено» (`0xEFF`). Betaflight розрізняє їх за контекстом: кадр версії очікується лише у відповідь на команду 13. З `FORCE` команди 13 немає, тож конфлікту немає. `0xEFF` як Status неможливий, бо біт 4 не використовується.

## 4. Порядок чергування

З увімкненим EDT кожна 32-га відповідь — EDT, по колу з шести типів:

```
температура → напруга → струм → status → debug 1 → debug 2 → температура → …
```

32 × 250 мкс = 8 мс між кадрами EDT. Кожен тип оновлюється раз на 6 × 8 = **48 мс** (≈ 20 разів на секунду). FC втрачає 1/32 відповідей з обертами (≈ 3 %).

## 5. Зміни в коді

### 5.1. Новий крейт `esc-emu` (логіка ESC)

`no_std`, workspace-член, залежить від `dshot-codec`. Сюди переїжджає з `src/main.rs` усе, що не залежить від заліза:

| Що | Звідки |
|---|---|
| модель eRPM (`ERPM_BASE`, `ERPM_PER_STEP`, `US_PER_MINUTE`, `reply_for`) | `src/main.rs` |
| модель струму (`current_for`) і нові моделі температури, напруги, Status | `src/main.rs` + нове |
| чергування EDT (`EDT_EVERY`, по колу з шести типів) | `src/main.rs`, розширено |
| `EdtSwitch` | лишається в кодеку; `Esc` його використовує |
| `EDT_AT_START` | **лишається в `src/main.rs`** (налаштування прошивки), передається в `Esc::new` |
| «забрати всі кадри, відповісти за останнім, після поганого CRC лишити останню добру відповідь» | `src/main.rs` |

API (як зроблено в кроці 2):

```rust
pub struct Esc { … }
pub struct Received {
    pub result: Result<Frame, FrameError>,
    /// `e12` кадру версії або «EDT вимкнено», коли щойно спрацювала команда 13/14 —
    /// прошивка пише це в лог defmt.
    pub edt_event: Option<u16>,
}
impl Esc {
    pub fn new(edt_at_start: bool) -> Self;
    /// Перша відповідь, до першого кадру ("мотор стоїть").
    pub fn first_reply(&self) -> u32;
    /// Один кадр з RX FIFO (сирий, інвертований); оновлює стан.
    pub fn on_raw(&mut self, raw: u32) -> Received;
    /// Наступна відповідь для TX FIFO; викликається раз на пробудження задачі.
    pub fn next_reply(&mut self) -> u32;
    pub fn edt_enabled(&self) -> bool;
}
```

Також публічні `reply_for`, `current_for` і константи моделі — тести перевіряють їх напряму.

**У кроці 3** `next_reply` отримує параметр `counters: Counters` — значення `bad` і `late` для Debug 1 / Debug 2: ESC не знає про USB і час, тож вони приходять з прошивки. У кроці 2 його ще немає, бо Debug ще не надсилається.

У `src/main.rs` лишаються залізо, PIO, USB і статистика, а задача PIO викликає `Esc`. Поведінка на лінії не змінюється, крім нових типів EDT і частоти 32.

**Тести `esc-emu`** — самостійні, на ПК, без заліза:
- як у `dshot-codec`: `#![cfg_attr(not(test), no_std)]` і `#[cfg(test)] mod tests` у `esc-emu/src/lib.rs` — для RP2040 крейт `no_std`, для тестів на ПК з `std`;
- запуск: `cargo test -p esc-emu --target x86_64-unknown-linux-gnu`, alias `cargo test-esc-emu` у `.cargo/config.toml` (як `test-codec`);
- роль FC у тестах грає `dshot-codec` (звичайна залежність, не dev): вхідні кадри — `encode_frame` з інверсією `!frame`, як їх бачить PIO; відповідь `Esc` розбирається через `decode_reply` і `decode_telemetry`.

| Тест | Що перевіряє |
|---|---|
| моделі за газом | для кожного газу з таблиці 2.1: оберти після e12, температура, напруга, струм, Status |
| команди | газ 0…47 → «мотор стоїть», температура 25, напруга 16,75, струм 0 |
| чергування EDT | за 6 × 32 відповідей кожен з шести типів проходить рівно раз, решта відповідей — період |
| поганий CRC | відповідь лишається за останнім добрим кадром |
| кілька кадрів за пробудження | одна відповідь, за останнім кадром |
| Debug 1 / Debug 2 | у кадрах EDT ті значення `bad` і `late`, що передані в `next_reply` |
| `edt_at_start = false` | до шести команд 13 поспіль EDT немає, потім один кадр версії `0xE02`, далі значення EDT |
| `edt_at_start = true` | EDT з першої відповіді, без кадру версії |

Спершу (крок 2) тести фіксують **поточну** поведінку — температура 42, EDT кожна 64-та, лише температура і струм, — щоб перевірити саме перенос. У кроці 3 вони оновлюються під нові моделі.

### 5.2. Кодек

`encode_voltage(steps)`, `encode_status(Status)`, `encode_debug1`, `encode_debug2`; розширити `Telemetry` (`Voltage`, `Status { alert, warning, error, max_stress }`, `Debug1`, `Debug2`), щоб розбирати їх явно, а не через `Other`. Тести round-trip для всіх нових типів.
