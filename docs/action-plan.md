## 1. Модуль кодування з тестами ✅

**Виконано** (коміти `dc62d1d`, `7bb923b`). Крейт `dshot-codec` — workspace-член, `no_std`, підключений до прошивки.

| Напрямок | Для RP2040 (ESC) | Для FC (тести, модель FC) |
|---|---|---|
| кадр FC → ESC | `decode_frame(raw) -> Result<Frame, FrameError>`, `frame_ok` | `encode_frame(Frame) -> u16` |
| відповідь ESC → FC | `encode_period`, `encode_reply` | `decode_reply`, `decode_period` |

`decode_frame` приймає значення прямо з RX FIFO (інвертовані біти) і сама робить інверсію та перевірку CRC. `Frame` містить `throttle` (0…2047) і `telemetry` (біт T), а `is_command()` відрізняє спеціальні команди (газ 0…47) від газу.

Тести (14, `cargo test-codec`):
- значення з документів: `encode_frame` газ 1000 → `0x7D05`, `decode_frame(0x82FA)` → газ 1000, `encode_reply(0x5F4) == 0x66A96800`, `encode_period(2000) == 0x5F4`;
- повний цикл для всіх 4096 кадрів (газ × T) і всіх 4096 значень e12;
- будь-яка одиночна помилка в кадрі ловиться CRC;
- межа `0xFFE`/`0xFFF` з `erpm-lower-limit.md`, похибка `encode_period` ≤ 1/256;
- форма відповіді: старт-біт, молодші 11 біт нульові, не більше 3 однакових рівнів підряд;
- межа команд і газу: 47 / 48.

**Перевірка:** `cargo test-codec`, `cargo build`, `cargo clippy` — без помилок і попереджень.

## 2. Стенд і еталонна осцилограма

**Ви:**
- зібрати стенд: FC ↔ GPIO0, спільна земля, аналізатор на лінії (крок 0);
- у Betaflight увімкнути `DSHOT300`, `dshot_bidir = ON`, `pid_process_denom = 2` (крок 1);
- записати кілька кадрів від FC (крок 2) і зберегти запис.

**Підключення.** RP2040 з прошивкою проєкту стоїть замість ESC на виході M1:

```
FC  M1 (сигнальний пад мотора) ──[220…470 Ом]── GPIO0  RP2040
FC  GND ─────────────────────────────────────── GND    RP2040
                                                GPIO3 → аналізатор (необов'язково)
```

- FC і RP2040 живляться кожен від свого USB; пади живлення ESC і батарею не підключати.
- Спільна земля обов'язкова: без неї `thr` стрибає або з'являється `BAD_CRC`.
- Рівні сумісні: вихід мотора FC (STM32) — 3,3 В, як і RP2040.
- Резистор у лінії необов'язковий, але бажаний: FC і RP2040 по черзі керують одним проводом, і якщо через помилку таймінгу вони колись увімкнуться одночасно, резистор обмежить струм. Детальніше — `series-resistor.md`.

**Налаштування Betaflight (CLI):**

```
set motor_pwm_protocol = DSHOT300
set dshot_bidir = ON
set pid_process_denom = 2
save
```

Очікувано: ESC є лише на M1, тож телеметрії з M2–M4 не буде, і Betaflight, імовірно, не дасть озброїтися. Для стенда це не заважає: тест моторів працює на неозброєному FC.

**Керування з ПК.** Газ на неозброєному FC задається з CLI (той самий механізм, що й повзунок у вкладці Motors):

```
#              вхід у CLI
motor 0 1477   M1 = 1477 (шкала 1000…2000; 1000 — стоп)
motor 0 1000   стоп
dshot_telemetry_info   що FC отримав у відповідь (eRPM, частка помилок)
exit           вихід (FC перезавантажиться)
```

Коли FC і RP2040 під'єднані до ПК, видно два порти `/dev/ttyACM*`: FC (VID `0483` для STM32) і RP2040 (VID `c0de`). Тоді Claude може сам задавати газ через CLI і звіряти його з виводом RP2040 — наприклад, автоматично пройти етап A (газ 1000…2000 → `thr` ≈ 48 + (v − 1001) × 1999 / 999, `bad=0`). Для цього потрібен доступ до порту (група `dialout`), а Configurator у цей час має бути закритий. Налаштування (`set`, `save`) і газ вище 1000 Claude змінює лише з вашого дозволу і наприкінці завжди повертає газ у 1000 (стоп).

**Claude:** допомогти з командами CLI; розібрати запис, якщо ви експортуєте його (CSV чи скриншот) — звірити біт 3,33 мкс, частки 75 % / 37,5 %, кадр ≈ 53,3 мкс.

**Готово, коли:** лінія в спокої висока, параметри кадру збігаються з таблицею кроку 2.

## 3. Етап A: прийом

**Claude — виконано** (коміт `a8a5317`; на стенді ще не перевірено):
- тактування PIO 12 МГц: дільник рахується від `clk_sys_freq()`, а не від жорстко вписаних 125 МГц (крок 3);
- PIO-програма прийому інвертованих кадрів (крок 4): `idle` чекає ≥ 5,3 мкс високого рівня, далі 16 разів «фронт → вибірка на 20-му такті → `wait 1 pin 0`», autopush на 16 біт. Чому саме так — `rx-bit-timing.pdf`;
- GPIO0: групи IN і JMP, підтяжка вгору, напрямок — вхід;
- CPU: кожне значення з RX FIFO одразу в `decode_frame(raw)`; лічильники кадрів і поганої CRC рахуються по **всіх** кадрах;
- USB: раз на 0,5 с текстовий рядок, дивитися просто `tio /dev/tty.usbmodem…` (без `hex4`):
  ```
  7D05 thr=1000 T=0 cmd=0 n=12345 bad=0
  7D04 BAD_CRC n=12346 bad=1
  ```
- GPIO3 (debug): короткий імпульс ≈ 170 нс у момент вибірки кожного біта;
- `cargo build`, `cargo build --release`, `cargo clippy` — без попереджень; README оновлено.

**Ви:**
- прошити (`cargo run --release` через debug-пробу, або з платою в BOOTSEL і runner `elf2uf2-rs -d`);
- дивитися вивід у `tio`, змінювати газ у Betaflight;
- на аналізаторі (GPIO0 + GPIO3): імпульси GPIO3 мають стояти приблизно посередині кожного біта, через ≈ 1,67 мкс після спаду.

**Готово, коли:**
- `n` зростає приблизно з частотою циклу FC (≈ 2 000 кадрів за 0,5 с при 4 кГц);
- `thr` відповідає газу у Betaflight, `T` і `cmd` — очікуваним значенням;
- `bad` ≈ 0 відносно `n`.

**Що повернути Claude, якщо не працює:** кілька рядків виводу `tio` і, якщо можна, запис аналізатора з GPIO0 і GPIO3 на одному кадрі.

**Стенд — виконано** (2026-10-13, `reports/001-first-try/findings.md`): `n` росте на ≈ 2024 за 0,5 с (≈ 4 кГц), `thr` іде за газом, `T=0`, `cmd=0`, `bad` 0,003–0,04 % і росте лише під час виводу в USB. Положення вибірки на GPIO3 не перевірено: сигналу на GPIO3 немає (пункт 7).

> **Як перевірити етап A з поточною прошивкою.** Поточна прошивка вже з етапом B (RP2040 відповідає на кадри) і з debug-ніжкою з пункту 7. Прийом у ній той самий, що й на етапі A (вибірка на 20-му такті), а імпульси на GPIO3 стоять там само, тож критерії етапу A перевіряються нею без змін. Прошивка лише з прийомом, без відповіді, — коміт `a8a5317` (`git checkout a8a5317 && cargo run`, потім `git checkout main`).

| Симптом | Імовірна причина |
|---|---|
| `no frames`, `n` не зростає | FC не в двонапрямному режимі (лінія в спокої низька) або немає сигналу на GPIO0 |
| `n` зростає, але майже всі `BAD_CRC` | вибірка не посередині біта (дивіться GPIO3), неправильна частота PIO |
| `n` зростає вдвічі повільніше, ніж очікувано | FC шле кадри рідше, ніж здається, або частина кадрів губиться в `idle` |
| `thr` стрибає при сталому газі | шум на лінії, погана земля, задовгі проводи |

## 5. Етап C: справжнє eRPM

**Claude:** замість константи — модель «газ → eRPM → період → `encode_period` → `encode_reply`» (крок 8); для спеціальних команд (`frame.is_command()`, газ 0…47) віддавати `encode_reply(E12_STOPPED)`.

**Claude — виконано** (коміт `61118dd`):
- модель з кроку 8: `eRPM = 1000 + газ × 20` (`ERPM_BASE`, `ERPM_PER_STEP` у `src/main.rs`) → період → `encode_period` → `encode_reply`;
- для спеціальних команд (газ 0…47) — `encode_reply(E12_STOPPED)`;
- після кадру з поганою CRC лишається відповідь за останнім добрим кадром;
- як і раніше, відповідь рахується за останнім кадром, який задача забрала з RX (`docs/rx-overflow-plan.md`);
- `cargo build`, `cargo build --release`, `cargo clippy` — без попереджень; README оновлено.

**Звідки константи:**
- **`60_000_000` (`US_PER_MINUTE`).** У відповіді передається не eRPM, а період одного електричного оберту в мікросекундах. eRPM — це оберти за хвилину, а в хвилині 60 × 1 000 000 = 60 000 000 мкс, тож період = 60 000 000 / eRPM. Наприклад, 30 000 eRPM → 2000 мкс.
- **`1000` (`ERPM_BASE`) і `20` (`ERPM_PER_STEP`).** Іграшкові значення для стенда з кроку 8, а не модель мотора. База 1000 тримає найповільнішу відповідь вище ≈ 919 eRPM, найменшого значення, яке вміщує e12 (`erpm-lower-limit.md`). Крок 20 дає на повному газі ≈ 42 000 eRPM, тобто ≈ 6 000 RPM.
- **`7` у RPM = eRPM / 7.** Кількість пар полюсів: Betaflight ділить eRPM на `motor_poles / 2`, а за замовчуванням `motor_poles = 14`. На один механічний оберт мотора з 7 парами полюсів припадає 7 електричних.

Очікувані значення (Betaflight показує RPM = eRPM / 7 при `motor_poles = 14`; e12 округлює період, тому eRPM трохи відрізняється від моделі):

| Газ (`thr`) | eRPM моделі | e12 | eRPM після e12 | RPM у Betaflight |
|---|---|---|---|---|
| 0…47 (команди) | — | `0xFFF` | 0 | 0 |
| 48 | 1 960 | `0xDDE` | 1 961 | 280 |
| 158 (холостий хід) | 4 160 | `0xBC2` | 4 167 | 595 |
| 500 | 11 000 | `0x954` | 11 029 | 1 576 |
| 1000 | 21 000 | `0x765` | 21 008 | 3 001 |
| 1500 | 31 000 | `0x5E3` | 31 056 | 4 437 |
| 2047 | 41 940 | `0x565` | 42 017 | 6 002 |

**Ви:** змінювати газ у вкладці Motors і дивитися, що оберти змінюються разом з ним; звіряти `thr` з `tio` і RPM з `dshot_telemetry_info` за таблицею.

**Готово, коли:** оберти у Betaflight відповідають моделі на всьому діапазоні газу.

**Стенд — виконано** (2026-10-15, release-збірка, `reports/003-day-three/findings.md`):
- ✅ Betaflight: газ 0 → 0, 48 → 2 000, 1000 → 21 000, 2047 → 42 000 eRPM (eRPM Betaflight округлює до сотень), Invalid 0 %;
- ✅ на осцилограмах декодовано відповіді `0xFFF` (газ 0) і `0x765` (газ 1000), рівні збігаються з `encode_reply`, CRC сходиться;
- ✅ `bad` = `txf` = 0, затримок задачі PIO немає;
- ⏳ телеметрію в Betaflight для проміжних значень (106, 1046) не знімали — `thr` у `tio` для них правильний.

> Обережно з `dyn_idle_min_rpm`: якщо він увімкнений, FC може підвищувати газ у відповідь на вигадані оберти (`throttle-explained.md`, розділ 6). На стенді краще `set dyn_idle_min_rpm = 0`.

## 7. Debug-ніжка (необов'язково)

**Claude — виконано** (на стенді ще не перевірено):
- GPIO3 повернуто через side-set: `.side_set 1` без `opt`, кожна інструкція має `side 0` або `side 1`; GPIO3 не мусить бути сусідом GPIO0, бо side-set — окрема група;
- поле затримки стало 4-бітним (максимум `[15]`), тому довгі затримки розбито з тим самим числом тактів:
  - `wait 0 pin 0 [19]` → `wait 0 pin 0 [15]` + `nop [2]` + `nop` — вибірка, як і раніше, на 20-му такті після фронту;
  - `out pins, 1 [30]` → `out pins, 1 [15]` + `nop [14]` — разом з `jmp` ті самі 32 такти на біт;
  - пауза `jmp y-- delay [15]` не змінилася;
- програма — 23 інструкції з 32;
- README оновлено.

Що показує GPIO3:

| Коли | GPIO3 |
|---|---|
| вибірка кожного біта кадру | імпульс 2 такти (≈ 170 нс) навколо вибірки, ≈ 1,67 мкс після спаду |
| RP2040 тримає лінію (відповідь, ≈ 56 мкс) | високий рівно від `set pindirs, 1` до `set pindirs, 0` |

**Ви:** на аналізаторі (GPIO0 + GPIO3) перевірити:
- таймінги прийому і відповіді ті самі, що в таблиці пункту 4;
- імпульси GPIO3 стоять приблизно посередині кожного біта кадру;
- високий рівень GPIO3 збігається з відповіддю на GPIO0, і в цьому вікні FC нічого не шле (інакше — конфлікт драйверів).

**Готово, коли:** усе вище збігається, а критерії пунктів 3 і 4 виконуються так само, як без debug-ніжки.

**Стенд — виконано** (2026-10-14, `reports/002-rx-overflow-fixed/findings.md`, розділ 4):
- ✅ голки GPIO3 на кожному біті кадру, високий рівень ≈ 55 мкс рівно на час відповіді, амплітуда ≈ 3,3 В; у першому запуску сигналу не було через налаштування осцилографа;
- ✅ у вікні відповіді FC нічого не шле;
- ✅ голки посередині біта: спад → голка 1,71 і 1,74 мкс (очікувано 1,58–1,75 мкс).
