# 004 — прогін «hardware in the loop»: FC керує RP2040

**Дата:** 2026-10-17. **Гілка:** `with-probe-rs`. **Прошивка RP2040:** коміт `c1793e8` (embassy-rp 0.9, етап C + EDT), release, прошита через probe-rs. **Проба:** від'єднана.

Claude сам задавав газ мотора 4 на FC з ПК і на кожному кроці читав телеметрію з двох боків:
- **FC:** що він отримав від «ESC»;
- **RP2040** (`/dev/ttyACM1`): який газ прийняв.

**Основний спосіб — CLI Betaflight** (розділ 2). Прогін через MSP — у додатку A. MSP вмикається **лише за потреби і за згодою користувача** (opt-in), див. A.0.

> **Коротко.**
> - **Обидва напрямки DShot працюють на всьому діапазоні газу (48…2047):** RP2040 приймає саме той газ, що задав FC (`bad=0`), а FC отримує оберти точно за моделлю етапу C з Invalid 0 %.
> - **Embassy 0.9 на стенді працює так само, як 0.4 у звіті 003:** перевірки з `migration-stage-2.md`, розділ 4, пройдені, крім EDT.
> - **EDT у Betaflight не ввімкнено:** TEMP і CURR 0, `edt=0`.
> - **Додаток A:** CLI і MSP переводять значення 1750 по-різному (1546 і 1547).

## 1. Стенд

| Порт | Пристрій | VID |
|---|---|---|
| `/dev/ttyACM0` | FC: `AT32_Virtual_Com_Port` | `2e3c` (Artery) |
| `/dev/ttyACM1` | RP2040: `DShot_logger` | `c0de` |

FC: Betaflight 2026.6.2, ціль `AT32F435M`, цикл 248 мкс (≈ 4 кГц), живлення від USB, неозброєний. Ці дані прочитано через MSP (додаток A.1); через CLI їх дає команда `status`.

RP2040 під'єднаний до виходу мотора 4 (у CLI це вихід 3), як у звітах 002 і 003. Справжнього мотора немає, тож «включити мотор» означає лише змінити газ у кадрах DShot.

Доступ до портів — через `sg dialout -c "…"`: група `dialout` додана, але в сесії Claude ще не діє (`findings-after-migration-stage-2.md`, розділ 2).

## 2. Прогін: CLI (`motor 3 …`)

Скрипт `hil/sweep_cli.py`:
1. `#` — вхід у CLI;
2. для кожного значення — `motor 3 <v>`, 1,5 с, `dshot_telemetry_info`, останній рядок USB з RP2040. Порт RP2040 відкривається в окремому процесі з тайм-аутом, бо відкриття вже зависало;
3. `motor 3 1000`, навіть при помилці;
4. `exit` — FC перезавантажився: «leaving CLI mode, unsaved changes lost, Rebooting». Нічого не збережено, налаштування не змінювалися.

|---|---|---|---|---|---|---|---|---|---|
| 1001 | 48 | **48** | `0609` | 2 000 | 286 | 4 | 0,00 % | 0 / 0 | 255 |
| 1250 | 546 | **546** | `444B` | 11 900 | 1 700 | 28 | 0,00 % | 0 / 0 | 258 |

## 3. Звірка з моделлю

Модель етапу C: eRPM = 1000 + газ × 20 → період = 60 000 000 / eRPM → `encode_period` (e12 округлює період униз) → назад у eRPM. Betaflight округлює eRPM до сотень, а RPM = eRPM / 7 (`motor_poles = 14`).

| Газ | eRPM моделі | e12 | eRPM після e12 | eRPM у Betaflight | RPM очікувано | RPM виміряно |
|---|---|---|---|---|---|---|
| 48 | 1 960 | `0xDDE` | 1 961 | 2 000 | 286 | **286** ✅ |
| 546 | 11 920 | `0x93A` | 11 943 | 11 900 | 1 700 | **1 700** ✅ |
| 1046 | 21 920 | `0x756` | 21 930 | 21 900 | 3 129 | **3 129** ✅ |
| 1546 | 31 920 | `0x5D5` | 31 983 | 32 000 | 4 571 | **4 571** ✅ |
| 2047 | 41 940 | `0x565` | 42 017 | 42 000 | 6 000 | **6 000** ✅ |
| 0 (команда) | — | `0xFFF` | 0 | 0 | 0 | **0** ✅ |

Усі значення збігаються точно.

## 4. Спостереження

### 4.1. RP2040 після міграції на embassy 0.9

- **`bad = 0` і `txf = 0`:** ≈ 3,28 млн кадрів від старту плати.
- **`gap` 254–325 мкс**, тобто задача PIO прокидається на кожен кадр.
- **`late = 1`** від старту плати і не змінювався під час прогону: ймовірно, один випадок при старті або під'єднанні FC.
- **Відповідь правильна на всіх значеннях газу,** тож PIO-налаштування в embassy-rp 0.9 (дільник, піни, side-set, зсув) працюють так само, як в 0.4.

Перевірки з `migration-stage-2.md`, розділ 4: `tio` з FC ✅, `dshot_telemetry_info` ✅, EDT ⏳. Осцилограф цього разу не використовувався.

### 4.2. EDT не ввімкнено

TEMP, CURR = 0, Type `R----`, у RP2040 `edt=0`. Betaflight не надсилав команду 13. Найімовірніше, `dshot_edt` вимкнено. Наступний крок — `set dshot_edt = ON`, `save` і повторити прогін: чекати Type `RT-C-`, TEMP 42 і CURR за таблицею з `docs/edt.md`, розділ 3.4. Перезавантаження після `exit` тут навіть допомагає: Betaflight, ймовірно, надсилає команду 13 саме при старті.

### 4.3. Перезавантаження FC після прогону

`exit` перезавантажує FC, тож на кілька секунд кадри DShot зникають. RP2040 побачить це як `late +1` і довгий `gap`, а порт FC зникне і з'явиться знову (номер `ACM*` може змінитися). Для наших тестів це не проблема.

## 5. Як повторити

Скрипт лежить у `hil/` поруч із цим звітом. Йому потрібен лише Python 3 без сторонніх пакетів. FC має бути неозброєний.

```
sg dialout -c "python3 reports/004-with-probe-rs/hil/sweep_cli.py /dev/ttyACM0 /dev/ttyACM1 1001,1250,1500,1750,2000"
```

| Скрипт | Що робить | Змінює FC? |
|---|---|---|
| `sweep_cli.py` | газ мотора 4 через CLI `motor 3 …`, `dshot_telemetry_info` і рядок RP2040; наприкінці 1000 і `exit` | газ мотора 4 (тимчасово); **`exit` перезавантажує FC** |

Порти визначати за VID (`udevadm info -q property -n /dev/ttyACM0 | grep ID_VENDOR_ID`): FC — `2e3c`, RP2040 — `c0de`. Номери `ACM0` і `ACM1` залежать від порядку під'єднання.

**Безпека.** Справжній ESC з мотором на виході 4 закрутиться — **гвинтів не ставити**. Скрипт завжди повертає газ у 1000, навіть якщо щось пішло не так.

## Додаток A. MSP (opt-in)

### A.0. Коли вмикати

MSP — двійковий протокол, яким користується Betaflight Configurator. Для наших тестів CLI достатньо, тому **MSP вмикається лише за потреби і за згодою користувача**. Claude сам MSP не використовує.

Коли MSP має сенс:

| Ситуація | Чому MSP |
|---|---|
| FC не можна перезавантажувати (довгий прогін, кілька тестів поспіль) | з CLI виходять лише через `exit`, а він перезавантажує FC |
| лише подивитися статус, нічого не змінюючи | читання через MSP не входить у CLI |
| перевірити шлях «як у Configurator» | вкладка Motors працює через `MSP_SET_MOTOR`; результат буває іншим, ніж через CLI (A.3) |

Мінуси: більше коду, треба знати номери команд і розкладку полів (вона теж змінюється між версіями Betaflight), і людині в терміналі цього не повторити.

### A.1. Статус FC (лише читання)

Скрипт `hil/fc_status.py` надсилає лише запити читання MSP v1: `MSP_API_VERSION`, `FC_VARIANT`, `FC_VERSION`, `BOARD_INFO`, `BUILD_INFO`, `STATUS_EX`, `ANALOG`, `MOTOR`, `MOTOR_TELEMETRY`. FC не перезавантажується.

| Що | Значення |
|---|---|
| Прошивка | Betaflight (`BTFL`) **2026.6.2**, MSP API 1.48, збірка 13.10.2026 |
| Плата | `A435`, ціль `AT32F435M` |
| Датчики | гіроскоп, акселерометр, барометр; помилок I2C 0 |
| Цикл | **248 мкс** (≈ 4 кГц), CPU 19 % |
| Живлення | 0,0 В / 0,0 А: батареї немає, FC живиться від USB |
| Виходи моторів | 1000 × 4 (неозброєний) |
| Телеметрія | мотори 1–3: Invalid 100 % (ESC немає); **мотор 4: Invalid 0 %**, RPM 0 (газ 0) |
| Чому не можна озброїти | прапорці `0x100004`: біт 2 — RX failsafe (немає приймача), біт 20 — RPM filter (немає телеметрії з моторів 1–3). Назви бітів — за списком Betaflight з пам'яті |

Обидві причини, чому FC не дає озброїтися, очікувані і тесту моторів не заважають.

### A.2. Прогін через `MSP_SET_MOTOR`

Скрипт `hil/sweep_msp.py`. Для кожного значення:
1. `MSP_SET_MOTOR` (214) з вісьмома значеннями: мотори 1–3 = 1000, мотор 4 = значення. Діє лише на неозброєному FC;
2. зачекати 1,5 с;
3. з FC — `MSP_MOTOR_TELEMETRY` (139) і `MSP_MOTOR` (104) для мотора 4;
4. з RP2040 — останній рядок USB.

Наприкінці, навіть при помилці, мотор 4 повертається в 1000. FC не перезавантажується.

| Задано | Вихід FC | `thr` на RP2040 | Кадр | RPM у FC | Invalid | `bad` / `txf` | `gap`, мкс |
|---|---|---|---|---|---|---|---|
| 1001 | 1001 | **48** | `0609` | **286** | 0 % | 0 / 0 | 258 |
| 1250 | 1250 | **546** | `444B` | **1 700** | 0 % | 0 / 0 | 254 |
| 1500 | 1500 | **1046** | `82C9` | **3 129** | 0 % | 0 / 0 | 319 |
| 1750 | 1750 | **1547** | `C164` | **4 571** | 0 % | 0 / 0 | 256 |
| 2000 | 2000 | **2047** | `FFE1` | **6 000** | 0 % | 0 / 0 | 311 |
| 1000 (повернення) | 1000 | — | — | **0** | 0 % | — | — |

Температура і струм на всіх кроках — 0, `edt=0`. RPM збігаються з CLI-прогоном і з моделлю (розділ 3): газ 1547 дає той самий e12 `0x5D5`, що й 1546, — різниця 20 eRPM губиться в округленні періоду.

### A.3. CLI і MSP переводять 1750 по-різному

| Шлях | 1750 → газ DShot |
|---|---|
| CLI `motor 3 1750` | **1546** |
| MSP `MSP_SET_MOTOR` | **1547** |

Решта значень (1001, 1250, 1500, 2000) однакові. За формулою 48 + (v − 1001) × 1999 / 999 виходить 1546,75. Схоже, CLI відкидає дріб, а шлях MSP округлює або рахує трохи інакше. Для стенда різниця в одну одиницю газу неважлива, тим більше що e12 її однаково губить. Але це показує, що два шляхи керування в Betaflight не ідентичні.
