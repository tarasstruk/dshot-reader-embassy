# 004 — спостереження після етапу 2 (embassy 0.9)

**Дата:** 2026-10-17. **Гілка:** `with-probe-rs`, коміт `c1793e8` (міграція на embassy-rp 0.9, `migration-stage-2.md`). **Збірка:** release, прошита через `probe-rs run`. **FC:** не під'єднаний.

> **Коротко.**
> - **USB працює:** прошивка на embassy 0.9 видає рядки телеметрії по USB, як і раніше.
> - **Порт інколи зависав:** перші спроби відкрити `/dev/ttyACM0` зависали. Після `probe-rs reset --chip RP2040` порт відкривається одразу.
> - **Причину точно не встановлено.** Найімовірніше, після зупинки `probe-rs run` ядро лишилося зупиненим, або порт відкривали, поки плата заново ставала на USB.
> - **Що робити, якщо зависне в тебе,** — розділ 4.

## 1. Вивід USB

Без FC на лінії, читання 3 с:

```
no frames n=0 bad=0 txf=0 late=0 gap=0 edt=0
no frames n=0 bad=0 txf=0 late=0 gap=0 edt=0
no frames n=0 bad=0 txf=0 late=0 gap=0 edt=0
…
```

| Що | Результат |
|---|---|
| частота рядків | рівно раз на 500 мс (7 рядків за 3 с, 368 байт) |
| формат | той самий, з полем `edt` |
| значення | без кадрів: `n=0`, усі лічильники 0, `edt=0` — так і має бути |
| налаштування порту | `tcgetattr`, raw-режим, 115200 — без помилок |

Порти (за `udevadm info`):

| Порт | Пристрій | VID | Група |
|---|---|---|---|
| `/dev/ttyACM0` | RP2040, `ID_MODEL=DShot_logger` | `c0de` | `dialout` |
| `/dev/ttyACM1` | Raspberry Pi Debug Probe (його UART) | `2e8a` | `plugdev` |

Номери `ACM0` і `ACM1` залежать від порядку під'єднання. Якщо під'єднано ще й FC, з'явиться третій порт. Завжди звіряйте VID: `c0de` — це наш RP2040.

## 2. Доступ до порту: група `dialout`

Порт RP2040 належить групі `dialout` з правами `crw-rw----`. Користувача додали в групу, але **нова група діє лише після повторного входу в систему**. У вже відкритих терміналах (і в сесії Claude) `id` її ще не показує, і відкриття порту дає `Permission denied`.

Обхід без перелогіну — запустити команду з групою `dialout` через `sg`:

```
sg dialout -c "tio /dev/ttyACM0"
```

`sg` пароля не питає, якщо користувач уже є в групі (`getent group dialout` → `dialout:x:20:taras`).

## 3. Зависання при відкритті порту

### 3.1. Що сталося, по черзі

| # | Коли | Дія | Результат |
|---|---|---|---|
| 1 | одразу після `probe-rs run` + Ctrl-C (прошивання о 10:55) | `stty -F /dev/ttyACM0 raw -echo` | **завис**, довелося зупинити |
| 2 | — | скрипт на Python: `open` з `O_NONBLOCK`, `tcsetattr`, читання 3 с | **завис**, зупинено через 10 с |
| 3 | — | `probe-rs reset --chip RP2040` | без помилок; порт `/dev/ttyACM0` створено заново (час 11:06) |
| 4 | одразу після скидання | той самий скрипт | **завис** ще раз |
| 5 | за кілька секунд | скрипт з журналом кожного кроку | відкрився одразу, прочитав 368 байт, закрився за 0,04 с |
| 6 | — | `open` + `tcsetattr` (raw, 115200) + `close` | усе за 0,04 с |
| 7 | — | скрипт із кроків 2 і 4 ще раз; `stty` ще раз | обидва працюють |

### 3.2. Що з цього випливає

- **Прошивка й USB працюють.** Після кроку 5 будь-яке відкриття і налаштування порту проходить миттєво, тож і `tio` має працювати.
- **Зависання зникло після скидання.** До скидання (кроки 1–2) порт зависав, після нього (кроки 5–7) — ні.
- **Причину точно не встановлено.** Є два пояснення:
  1. **Ядро лишилося зупиненим після `probe-rs run`.** Відкриття порту надсилає на USB службові запити (DTR, швидкість). Якщо процесор RP2040 стоїть, на них ніхто не відповідає, і ядро Linux чекає. Порт при цьому існує, бо плата стала на USB ще до зупинки. Скидання знову запускає прошивку.
  2. **Порт відкривали надто рано.** Після скидання (крок 4) плата щойно заново ставала на USB, тож запит міг потрапити в цей момент.

  Крок 4 показує, що одного пояснення 1 недостатньо. Можливо, працюють обидва.
- **Перевірити пояснення 1** можна так: після `probe-rs run` і Ctrl-C подивитися, чи стоїть ядро, — наприклад, `probe-rs attach --chip RP2040 …` або `probe-rs read` регістра стану. Цього не робили.

## 4. Що робити, якщо `tio` (або інша програма) зависає на відкритті порту

Іти по кроках, доки не запрацює.

**Крок 1. Чи це той порт.**

```
for d in /dev/ttyACM*; do echo "$d $(udevadm info -q property -n $d | grep ID_VENDOR_ID)"; done
```

Потрібен порт з `ID_VENDOR_ID=c0de`. Порт проби (`2e8a`) відкривається, але показує інше.

**Крок 2. Чи є доступ.**

```
ls -l /dev/ttyACM0     # група dialout
id                     # чи є dialout серед груп
```

Якщо `dialout` у `id` немає — перелогінитися або запускати через `sg dialout -c "tio /dev/ttyACM0"` (розділ 2). Відсутній доступ дає `Permission denied` одразу, а не зависання.

**Крок 3. Чи порт не тримає інша програма.**

```
pgrep -a tio; pgrep -a probe-rs
```

Закрити зайвий `tio`. Якщо висить `probe-rs run`, зупинити його Ctrl-C у його терміналі; якщо не відповідає — `kill <PID>`, у крайньому разі `kill -KILL <PID>` (так було в етапі 1, `migration.md`, крок 4).

**Крок 4. Запустити прошивку заново через пробу.**

```
probe-rs reset --chip RP2040
```

Скидає RP2040 і запускає прошивку. Після цього **зачекати 2–3 секунди**, поки плата заново стане на USB (порт `/dev/ttyACM*` з'явиться знову), і лише потім відкривати `tio`.

**Крок 5. Якщо проби немає або скидання не допомогло.**

Від'єднати USB-кабель RP2040 і під'єднати знову (або натиснути RESET на платі), зачекати 2–3 секунди, відкрити `tio`.

**Крок 6. Якщо зависає знову і знову.**

Зібрати для Claude:
- `dmesg | tail -30` — повідомлення ядра про USB (`cdc_acm`, помилки `-110` = тайм-аут);
- `lsusb | grep -i c0de` — чи плата взагалі на USB;
- вивід `probe-rs run` (`cargo run --release`): чи стартувала прошивка (рядок `[INFO ] dshot-reader-embassy: …`) і чи немає паніки.

**Як не наступати на це:** після прошивання через `cargo run --release` закривати `probe-rs` (Ctrl-C) і, якщо `tio` не відкривається, робити крок 4. Або тримати `probe-rs run` відкритим, поки працюєш з `tio`: тоді він сам стежить за ядром і показує логи defmt.
